# VFXTool 2차 A 판 — Unity 한 번 띄워 여러 판 굽기(묶어 굽기) 설계

> 2026-10-22 · 근거 : 7판 실측 `startup_ratio` 0.977(`../Research/2026-10-15-VFX툴구현실측.md` 「7판」 절) · 앞 설계 `2026-10-15-변형묶음설계.md` 10절 · D1
> 바탕 계약 : `2026-10-14-VFX툴설계.md` 5-4(job.json · result.json · 종료 코드)

## 0. 결론 먼저

- `vfxtool variant run` 이 **Unity 를 한 번만 띄워** 펼친 판을 다 굽는다. 지금은 판마다 띄워서 12판에 212초, 그중 Unity 안 시간은 4.9초다.
- 기존 `-vfxJob <job.json>` 계약은 **한 글자도 안 바꾼다.** 새 인자 `-vfxJobs <jobs.json>` 만 더한다. 목록 안의 판마다 job.json · result.json 은 지금 꼴 그대로다.
- C# 은 목록을 돌며 판마다 새 `VfxResult` + try/catch 로 굽고, 결과는 **각 job.json 옆 result.json** 에 쓴다. 판 하나의 예외는 그 판만 실패다.
- Python 은 「준비 → Unity 한 번 → 판마다 마무리」 세 토막으로 돈다. 판별 결과는 **판별 result.json 만** 믿는다.
- Unity 가 죽거나 시간을 넘기면 **result.json 이 없는 판만 모아 한 번 더** 묶어 돌린다. 그래도 없으면 그 판들만 failed(`variant.unity_lost`).
- 기본이 묶음이다. `--each` 를 주면 옛 동작(판마다 따로)이다. 단일 `loop` · `build` · `render` 는 안 바뀐다.
- 관문은 「`--each` 와 PNG 바이트가 100% 같다 · 12판 40초 이하」다(7절).

## 1. 목표와 범위

7판 실측에서 판 하나 17.4초 중 Unity 안 일(build + render)은 0.4초였다. 나머지는 Unity 기동 · 패키지 가져오기 · 종료다. 판 수만큼 이 값을 다시 낸다. 묶어 굽기는 이 값을 **한 번만** 낸다. 이론값은 12판 212초 → 약 25초다.

| 하는 것 | 안 하는 것 |
| --- | --- |
| C# `-vfxJobs` 목록 실행 · 판별 결과 · 판 사이 로그 줄 | B 판 「속성 전용 소재 층(번개 모양)」 — 다음 판 |
| Python `variant run` 묶음 경로 · 재시도 한 번 · `--each` | 단일 `loop` 의 바퀴 묶기 — 바퀴는 앞 바퀴 결과를 보고 고치므로 묶을 수 없다 |
| timing 정의를 묶음 기준으로 다시 적기 | Unity 를 계속 띄워 두는 상주 서버(파이프 · 소켓) — 계약이 커진다. 묶음으로 충분한지 먼저 본다 |
| 가짜 Unity 손잡이 · 시험 · 실측 관문 | 여러 Unity 를 동시에(병렬) — 같은 프로젝트를 둘이 못 연다(D1) |

## 2. 계약

### 2-1. Unity 인자

```
-batchmode -projectPath <프로젝트> -logFile <묶음>/unity.log
-executeMethod Officina.Vfx.Editor.VfxEntry.Run -vfxJobs <묶음>/jobs.json
```

- 진입 메서드는 **같은 `VfxEntry.Run`** 이다. `-vfxJob` · `-vfxJobs` 중 **하나만** 있어야 한다. 둘 다 있거나 둘 다 없으면 종료 2.
- `-vfxJob` 경로는 지금 코드 그대로 돈다.

### 2-2. `jobs.json` 꼴

```json
{ "jobs": [ "D:/fxwork/hit/hit_fire_mid_s0/job.json",
            "D:/fxwork/hit/hit_fire_mid_s1/job.json" ] }
```

- 칸은 `jobs` 하나. C# 모델 `VfxJobList` 도 `MissingMemberHandling.Error` 로 읽는다(모르는 칸 = 오타).
- 원소는 **절대 경로 문자열**이다. 상대 경로 · 빈 글 · 같은 경로 두 번 · 1개 미만 · 48개 초과는 목록 오류(종료 2, 어느 판도 안 굽는다). 48은 묶음 판 수 상한과 같다.
- 자리는 묶음 폴더 바로 아래 `jobs.json`. Python 이 판마다 덮어쓴다(재시도 때는 남은 판만).
- 판마다 job.json 은 **지금 `make_job` 꼴 그대로**(`recipe · mode · saveRoot · outDir · frames · backgrounds`). `test_write_job_fields` 의 칸 고정은 그대로 지켜진다.

### 2-3. 결과 자리

| 무엇 | 자리 | 누가 씀 |
| --- | --- | --- |
| 판 결과 | 각 job.json 옆 `result.json`(= 판 폴더) | C#, 판 하나 끝날 때마다 바로 |
| 판 프레임 | 판 job 의 `outDir`(= 판 폴더 `frames/`) | C# |
| 묶음 로그 | 묶음 폴더 `unity.log` 한 개 | Unity |
| 판 로그 | 따로 없다. Python 이 묶음 로그에서 그 판 토막을 잘라 읽는다(2-5) | — |

판이 끝날 때마다 바로 쓰므로, 도중에 Unity 가 죽어도 앞 판 결과는 남는다. 재시도가 이것을 쓴다(4절).

### 2-4. 종료 코드

| 코드 | 뜻 |
| --- | --- |
| 0 · 1 · 2 | 판별 `ExitCode()` 의 **최댓값**. 판 하나라도 error 면 2 |
| 2 | 목록 오류(2-2) — 판별 result.json 을 하나도 안 쓴다 |

Python 은 종료 코드로 판을 가르지 않는다. **판별 result.json 의 status** 를 믿는다. 종료 코드는 「목록 오류인가」를 가를 때만 본다(4절).

### 2-5. 로그 줄

| 줄 | 언제 |
| --- | --- |
| `[VFXTOOL] jobs n=12 list=<jobs.json>` | 목록을 읽은 직후 |
| `[VFXTOOL] job=<job.json> mode=… recipe=… layers=…` | 판 시작 (지금 `RunJob` 줄 그대로) |
| `[VFXTOOL] item 3/12 status=ok issues=0 frames=14 exit=0 result=<result.json>` | 판 끝 (result.json 을 쓴 뒤) |
| `[VFXTOOL] jobs done n=12 exit=<최댓값>` | 끝, `EditorApplication.Exit` 직전 |
| `[VFXTOOL] jobs error=<글>` | 목록 오류. 이 줄이 있으면 Python 은 재시도하지 않는다 |

판 토막 = 그 판 `job=<경로>` 줄부터 다음 `item i/n` 줄까지. `log_issues` · `no_result_lines` 는 이 토막만 읽어 판 issue 에 붙인다. 묶음 로그 전체를 판마다 붙이면 한 판의 예외가 열두 판에 다 붙는다.

## 4. 실패 · 재시도 흐름

### 4-1. `run_set` 묶음 경로

1. **준비** — 이름 순으로 판마다 `prepare_round`(check · resolved) → `command.prepare`(job.json · 옛 result 지우기). 여기서 떨어진 판은 바로 failed(지금과 같은 rule)이고 목록에 안 넣는다.
2. **굽기** — 남은 판으로 `jobs.json` 을 쓰고 `run_unity` 한 번. 시간 상한은 5-2.
3. **빈 판 모으기** — result.json 이 없는 판을 모은다.
   - 없으면 4로.
   - 로그에 `jobs error=` 가 있으면 재시도 없이 **종료 2**(목록 오류 = 툴 버그).
   - 아니면(Unity 가 죽음 · timeout · 이유 모름) **빈 판만으로 한 번 더** 2를 돈다. 두 번째 판의 상한은 그 판 수로 다시 셈한다.
4. **마무리** — 판마다 `command.finish` → `finish_round` → `finish_one`(장부 칸). 두 번째에도 result 가 없는 판은 failed + `variant.unity_lost` error(detail = 첫 판 · 둘째 판 종료 코드와 토막 로그 줄). 판마다 `set.json` 을 쓴다(지금과 같은 수법, 끊겨도 이어 돈다).
5. 끝나면 sheet(지금 그대로).

### 4-2. 실패 종류별

| 일 | 판 | 묶음 |
| --- | --- | --- |
| C# 관리 예외(레시피 틀림 · 툴 버그) | 그 판 result.json status=error → failed(`entry.exception` · `entry.bug` 그대로) | 다음 판 계속 |
| Unity 가 판 k 에서 죽음(네이티브 크래시) | k 앞은 result 있음 → done. k 와 뒤는 재시도 | 프로세스 한 번 더 |
| timeout | 끊긴 자리 앞은 done, 나머지 재시도 | 같음 |
| 재시도에서도 빈 판 | failed + `variant.unity_lost` | 다른 판은 그대로 |
| 목록 오류(`jobs error=`) | 전부 그대로 expanded(손대지 않음) | 종료 2 |
| 준비 단계 실패(check · 텍스처 경로) | failed, 목록에 안 넣음 | 계속 |

옛 result.json 은 1단계에서 지운다(`_clear_old_results`). 그래서 「result 가 있다 = 이번 Unity 가 썼다」가 성립한다. 판 폴더의 `unity.log` 는 묶음 경로에서는 안 쓴다(지우기만 한다).

## 5. timing 정의

### 5-1. 칸

| 칸 | 묶음 경로 | `--each` |
| --- | --- | --- |
| 판 `seconds.wall` | null — 판별 벽시계가 없다 | 지금 그대로 |
| 판 `seconds.unity_build` · `unity_render` | 그 판 result.json `seconds` | 그대로 |
| `timing.wall_total` | `run_set` 1단계 시작 ~ 4단계 끝(sheet 뺌) 벽시계 한 번 | 판 wall 합(지금) |
| `timing.unity_inside` | 셈한 판 build + render 합 | 그대로 |
| `timing.unity_wall`(새) | Unity 프로세스 벽시계 합(재시도 포함) | 판마다 잰 것 합 |
| `timing.per_variant_mean` | `wall_total ÷ measured` | 그대로 |
| `timing.mode`(새) | `"batch"` | `"each"` |
| `timing.retries`(새) | 재시도 프로세스 수(0 또는 1) | 0 |
| `timing.startup_ratio` | 1 − `unity_inside ÷ wall_total` | 그대로 |
| `timing.measured` | done 이고 build · render 가 있는 판 수 | 그대로 |

- `startup_ratio` 는 꼴이 같다. 뜻만 「판 벽시계 합」에서 「묶음 벽시계 한 번」으로 바뀐다. 묶음에서는 Unity 기동이 한 번만 들어가므로 판이 많을수록 낮아진다.
- `variant.startup_heavy` 문턱은 **0.5 그대로**다. 12판 묶음이 25초 · 안 4.9초면 0.80 이라 여전히 뜬다. 이 뜻은 「기동 한 번도 아직 무겁다」이다 — 문구를 `--each` 일 때는 지금 글, 묶음일 때는 「Unity 기동 한 번이 묶음 시간의 대부분이다(판이 적거나 기동이 느림)」로 가른다.

### 5-2. 시간 상한

- 묶음 상한 = **60초 + 판 수 × 20초**(판당 20초는 초안. 실측 뒤 판당 render 최댓값 × 3 쯤으로 고친다).
- `--timeout` 기본은 None. `--each` 면 None → 지금 300초(판 하나 상한). 묶음이면 None → 위 셈, 값을 주면 **그 값이 묶음 하나의 상한**(재시도도 같은 값).

## 6. 시험 목록

### 6-1. 가짜 Unity 손잡이 (`fake_unity.py`)

| 손잡이 | 하는 일 |
| --- | --- |
| `-vfxJobs <파일>` | 목록을 읽어 판마다 지금과 같은 result.json 을 **job.json 옆**에 쓰고 2-5 의 item 줄을 로그에 남긴다 |
| `--die-at k` | k번째 판(1부터) 시작 때 result 없이 종료 코드 3 으로 끝난다 |
| `--die-once <표시 파일>` | 표시 파일이 없으면 만들고 `--die-at` 대로 죽는다. 있으면 안 죽는다 — 재시도 성공 시험용 |
| `--fail-at k` | k번째 판만 status=error result(관리 예외 흉내) |
| `--list-error` | `jobs error=` 줄만 남기고 종료 2 |
| 지금 손잡이 | `--sleep` · `--frame-png` 등 그대로. `--sleep` 은 판마다 걸어 timeout 시험에 쓴다 |

`-vfxJob` 하나일 때는 지금처럼 `outDir` 에 쓴다(기존 시험 안 건드림).

`--die-at` 이 늘 죽으면 둘째 판에서 목록이 5~12 로 줄어 「목록 안 5번째 = 9번」에서 죽는다. 시험은 이 셈을 그대로 기대값으로 쓴다(5~8 은 둘째 판에 done, 9~12 failed). 손잡이 뜻을 「목록 안 순번」으로 고정해 헷갈림을 없앤다.

## 7. 관문

같은 12판(7판 실측의 hit_sparks 묶음, 설계 2-1 예제)을 시험 Unity 프로젝트에서 `--each` 와 묶음으로 한 번씩 돌린다.

| # | 관문 | 기준 |
| --- | --- | --- |
| G1 | 프레임 PNG 바이트 | 두 경로 판별 · 장별 **100% 같음** |
| G2 | 12판 벽시계(`wall_total`) | **≤ 40초** |
| G3 | 판 상태 | done 12 · error 0 · warn 0 |
| G4 | 가짜 Unity 「k번째에서 죽기」 | k 앞 첫 판에 done · 뒤는 재시도로 done |
| G5 | 상태 새기 | 마지막 판 render 초 ≤ 첫 판 render 초 × 1.5 |
| G6 | 기존 시험 | pytest · EditMode 모두 통과(골든 resolved 안 바뀜) |

고리 : **작업 → 시험 → 원인 → 작업** 을 최대 3번 돈다. 고리마다 원인 한 줄을 구현실측 문서 「2차 A」 절에 적는다. 3번 안에 G1 · G3 이 안 되면 묶음을 기본에서 내리고(`--batch` 로 켜기) 보고한다.

## 9. 결정 표

| # | 결정 | 까닭 |
| --- | --- | --- |
| A1 | `-vfxJob` 그대로 · `-vfxJobs <jobs.json>` 만 추가 · 진입 메서드는 같은 `Run` | 단일 `build` · `render` · `loop` 와 기존 시험을 안 건드린다. `build_args` 의 메서드 이름도 그대로 |
| A2 | `jobs.json` = `{"jobs":[절대 경로…]}`, `MissingMemberHandling.Error`, 1~48개 · 겹침 금지 | job 계약과 같은 엄격함. 판 칸은 job.json 에 이미 있다. 겹치면 result 를 덮는다 |
| A3 | 판마다 `new VfxResult` + try/catch, result 는 각 job.json 옆에 바로 | 한 판의 예외가 다른 판을 오염시키지 않는다. 죽어도 앞 판 결과가 남는다 |
| A4 | 종료 코드는 최댓값, Python 은 판별 result.json 을 믿음 | 묶음 하나의 코드로는 판을 못 가른다 |
| A5 | 판 사이 로그 `[VFXTOOL] item i/n status=…` · 판 토막만 판 issue 에 | 어디서 죽었는지 로그만 봐도 안다. 남의 판 예외가 안 붙는다 |
| A6 | `command._execute` → `prepare` · `finish`, `run_pipeline` → `prepare_round` · `finish_round`. 단일은 이어 부름 | 판별 마무리 로직을 한 벌로 유지(두 벌이면 어긋난다) |
| A7 | `run_set` = 준비 → Unity 한 번 → 판마다 마무리 + set.json | 판 하나 끝날 때마다 장부를 쓰는 지금 수법 유지 |
| A8 | 죽음 · timeout 이면 빈 판만 **한 번** 더, 그래도 없으면 failed `variant.unity_lost` | 크래시 한 번에 남은 판을 다 잃지 않게. 두 번 넘게는 같은 판이 계속 죽일 수 있어 끝이 없다 |
| A9 | 묶음 상한 = 60초 + 판 수 × 20초(초안) | 기동 한 번 + 판당 여유. 판당 값은 실측 뒤 고친다 |
| A10 | timing 은 묶음 벽시계 한 번 + 판별 Unity 안 초, `startup_ratio` 꼴은 그대로, 문턱 0.5 그대로 | 보고 꼴을 안 깨고 뜻만 다시 적는다 |
| A11 | 기본 묶음, `--each` 로 옛 동작 | 빠른 쪽이 기본. 묶음이 의심될 때 바로 견줄 길(G1)이 남는다 |
| A12 | 관문 G1~G6(7절) | 바이트 같음이 「묶어도 결과가 안 바뀐다」의 유일한 확실한 증거 |
| A13 | 작업→시험→원인→작업 최대 3번, 원인 한 줄씩 | 공용 고리 규칙 |
| A14 (새) | `jobs error=` 가 있으면 재시도 없이 종료 2 | 목록 오류는 다시 돌려도 같다. 17초를 버리지 않는다 |
| A15 (새) | `--timeout` 기본 None — `--each` 는 300초, 묶음은 A9 셈, 값을 주면 묶음 하나 상한 | 인자 하나로 두 경로를 받는다. 새 인자를 안 늘린다 |
| A16 (새) | 묶음 경로의 판 `seconds.wall` 은 null | 판별 벽시계가 없다. 가짜 값을 넣으면 사람이 속는다 |
| A17 (새) | 가짜 Unity `--die-at k` 는 「목록 안 순번」 | 재시도 때 목록이 줄어 순번 뜻이 흔들리지 않게 |
| A18 (새) | 3번 안에 G1 · G3 이 안 되면 묶음을 기본에서 내림 | 결과가 다를 수 있는 길을 기본으로 두지 않는다 |
| A19 (리뷰 뒤) | 묶음에서는 `variant.startup_heavy` 를 안 낸다. `--each` 에서만 | 그 info 는 「묶어 굽기를 하라」는 뜻인데 이미 묶음이다. 12판 묶음도 0.941 로 늘 떴다 |

A1~A13 은 메인이 정한 권장안 그대로다. A14~A18 은 이 설계에서 더한 세부다.

### 9-1. 대안 (바꾸지 않고 적어 둠)

| 자리 | 대안 | 까닭 · 언제 |
| --- | --- | --- |
| A8 재시도 순서 | 재시도 목록에서 **첫 빈 판(죽인 판일 가능성이 큼)을 맨 뒤로** 보낸다 | 그 판이 정말 Unity 를 죽이는 판이면, 지금 순서로는 재시도에서도 맨 앞에서 죽어 뒤 판을 또 다 잃는다. 맨 뒤로 보내면 그 판 하나만 잃는다. 바뀌는 건 목록 순서 한 줄이다. 실측에서 재시도가 한 번이라도 또 죽으면 이것으로 바꾼다 |
| G5 견줌 | 「첫 판 · 끝 판」 대신 **같은 세기 · 같은 시드끼리 처음과 끝**을 견준다 | 판은 이름 순(fire → … → lightning, weak/mid/strong 이 섞임)이라 첫 판과 끝 판의 세기가 다를 수 있다. strong 은 입자가 2배쯤이라 render 초가 달라 상태 새기와 섞인다. 실측 표에서 세기별로 같이 적어 두고 판정은 메인 기준을 쓴다 |
| A9 판당 값 | 판당 값 대신 「마지막 item 줄 뒤 N초 안에 다음 item 줄이 없으면 끊기」(진행 감시) | 판 수에 덜 민감하다. 다만 로그 파일을 돌며 읽는 코드가 는다. 판 수가 48 가까이 커져 상한이 16분을 넘는 일이 잦으면 본다 |

## 구현 뒤 정정

구현이 이 설계와 다르게 한 것. 실측은 `../Research/2026-10-15-VFX툴구현실측.md` 「10-22 2차 A」 절.

| 쪽 | 설계 | 구현 |
| --- | --- | --- |
| C# | 목록 겹침 검사 | **판 폴더 기준 · 대소문자 무시**로 겹침을 본다 |
| C# | `-vfxJob` · `-vfxJobs` | 둘 다 주면 `jobs error=` 줄 뒤 **종료 2**. 둘 다 없으면 옛 단일 오류 그대로 |
| C# | 목록 오류 글 | 글 앞에 **예외 이름**을 붙인다(`IOException: …`) |
| C# | 로그 토막 | RunJob 앞에서 실패한 판은 `job=` 줄이 없다 → 토막은 **`item` 줄 기준**으로 자른다 |
| Python | 묶음 시간 칸 | `set.json` 최상위 `run` 칸 `{mode, wall, unity_wall, retries, variants}`. `--each` 는 `{mode}` 만, timing 의 `unity_wall` 은 null |
| Python | 재시도 로그 | 재시도 판 로그는 `unity_retry.log` |
| Python | 판 가르기 | 묶음 경로는 프로세스 종료 코드로 판을 가르지 않고 **판 result.json 의 status 만** 본다 |
| Python | 재시도 순서(9-1 대안 1) | **대안 1 채택** — 재시도 목록에서 첫 빈 판을 맨 뒤로 보낸다. 늘 죽이는 판이 있어도 그 판만 잃는다 |
| Python | 로그 토막 기준(2-5) | `job=` 줄이 아니라 **`item` 줄** 기준(앞 item 줄 다음 ~ 이번 item 줄). 토막을 못 찾은 판은 info `variant.log_span` |
| Python | `startup_heavy` | 묶음에서는 안 낸다(A19). `--each` 에서는 그대로 |
| Python | `run.variants` 뜻 | 돌릴 판 전부가 아니라 **Unity 에 실제로 넘긴 판**(준비에서 떨어진 판은 뺌) |
