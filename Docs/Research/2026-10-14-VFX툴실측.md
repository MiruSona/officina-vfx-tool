# VFXTool 실측 — 설계 전 스파이크 넷 + 추가 실측 A~D (2026-10-14)

**한 줄 요약** : `-batchmode` 만으로 URP 2D 렌더러에서 파티클 프레임 PNG 를 뽑을 수 있고, 같은 seed 면 바이트까지 같다.
투명 알파는 **후처리만 끄면** 산다(HDR 무관). 도트 격자 맞추기는 **스냅 셰이더**(입자 중심만 텍셀에 반올림)가 Upscale RT 와 같은 그림을 낸다.

앞선 조사(`2026-10-14-VFX툴조사.md` 5-2 절)는 「배치 모드 + URP 2D 에서 실제로 그려지나」를 가장 큰 위험으로 꼽고, 설계 전에 스파이크 넷으로 가르자고 했다.
조사 단계에서는 Unity 를 한 번도 돌리지 않았다. 이 문서는 그 넷을 실제로 돌린 결과와, 넷이 끝난 뒤 더 본 것 넷(A 픽셀 스냅 · B Noise · C additive 겹침 · D 2D 빛·HDR 64bit)을 정리한다.

게임 저장소의 카메라·렌더 설정은 아래와 같다. 실측 조건을 고를 때 기준으로 삼았다.

## 1. 스파이크 넷

### ① batchmode 에서 GPU 렌더가 되나

- **물음** : `-nographics` 없이 `-batchmode` 만 쓰면 빈 2D URP 씬의 파티클이 PNG 에 그려지나.
- **결과** : **통과.** 256² 중 흰 픽셀 1248, 배경 (128,128,128). 회색 빈 그림이 아니다. 두 판 모두 로그에 `error CS`·`Exception` 없음.
- **설계에 미치는 것** : 실행기는 `-batchmode` 만 붙인다. 화면 없는 서버(GPU 없음)에서는 못 돈다.

### ② 2D 렌더러에서 SingleCameraRequest 가 되나

- **물음** : `RenderPipeline.SupportsRenderRequest(cam, new SingleCameraRequest())` 가 2D 렌더러에서 true 인가. 안 되면 `Camera.Render()`.
- **결과** : **통과.** true 이고 실제로 그려진다. `Camera.Render()` 도 같은 결과(흰 1248, 무게중심 같음).
- **설계에 미치는 것** : 프레임 뽑기는 `SingleCameraRequest` 하나로 간다. `Camera.Render()` 는 대비책으로만 둔다.

### ③ 투명 PNG 알파가 살아 나오나

- **물음** : Solid Color (0,0,0,0) + ARGB32 RT 로 뽑을 때 알파가 남나. URP 에셋 HDR 설정별로.
- **결과** :

| 조건 | 알파 | 수치 |
| --- | --- | --- |
| HDR 켬 · 후처리 끔 | **삶** | 바깥 64459 픽셀 알파 전부 0, 입자 1077 픽셀 알파>0 |
| HDR 끔 · 후처리 끔 | **삶** | 같은 꼴 |
| HDR 켬/끔 · 후처리 켬(FXAA) | **죽음** | 배경이 (0,0,0,255). 알파 0 인 픽셀 0개 |
| 후처리 켬 · AA 없음 | **죽음** | 같은 꼴 — FXAA 탓이 아니라 후처리 자체 |
| 후처리 끔 · FXAA 지정 | 삶 | 후처리가 꺼지면 AA 값은 상관없음 |
| additive(Particles/Unlit) · 색 One One · 알파 One One | 있음 | 입자 알파 1.0 |
| additive · 색 One One · 알파 **Zero One** | **0** | 색은 그려지는데 maxA=0.00 → 투명 PNG 에서 안 보임 |

- **놀란 것** : 조사 문서가 걱정한 「HDR 32bit 가 알파를 지운다」는 이 조건(2D 렌더러 + ARGB32 대상 RT + 후처리 끔)에선 안 나타났다. 64bit 도 같다(→ D).
- **설계에 미치는 것** : 뽑는 카메라는 `renderPostProcessing = false` 를 강제한다. HDR 은 건드리지 않는다.
  additive 머티리얼은 알파 블렌드를 One One 으로 고정한다.

### ④ Simulate 가 결정적인가

- **물음** : `Simulate(t, true, restart:true)` 로 같은 t 를 두 번 뽑으면 픽셀이 같나.
- **결과** : **통과.** seed 1234, t=0.3. 같은 씬 두 번 · 새 씬에서 다시 만들어도 PNG SHA256 이 같다.
  시간열 t=0.0~0.9 는 무게중심 y 가 0.1초에 약 8px 씩 고르게 오른다(0.1:71.7 → 0.9:136.3).
- **함정** : t=0 은 입자 0개다. t=0 버스트도 아직 안 나온다. **첫 프레임은 빈 그림**이다.
- **머티리얼** : URP `Particles/Unlit`(분홍 0, 흰 1160, `isSupported`=true) · `Sprite-Unlit-Default` 둘 다 2D 렌더러에서 정상.
- **못 가른 것** : 이 판의 `fixedTimeStep` true/false 해시가 같았다. 직선 운동뿐이라 차이를 가를 수 있는 시험이 아니었다 → B 에서 다시 봤다.
- **설계에 미치는 것** : 프레임 i 의 시각은 t=i/fps 그대로 쓰되, 첫 프레임을 1/fps 부터 뽑거나 i=0 을 빈 그림으로 받아들인다.

## 2. 추가 실측 A~D

공통 조건 : RT 1024², ortho size 4 → 128 px/unit. PPU 32 이므로 텍셀 1개 = 화면 4×4 px.
입자는 흰 2×2 Point 텍스처, 크기 2 텍셀(8×8 px), 버스트 30, seed 1234, World 공간, 투명 배경, MSAA 끔.

### A. 픽셀 스냅 다섯 방식

도트풍이면 입자가 텍셀 격자(여기선 4 px 단위)에 맞춰 놓여야 한다. 다섯 방식을 t=0.35 한 장으로 견줬다.
지표 ① = 흰 픽셀 가로·세로 경계 중 4의 배수 좌표에 놓인 비율. 지표 ② = 배경도 흰도 아닌 중간색 픽셀 수.

| 방식 | 지표 ① | 지표 ② | 비고 |
| --- | --- | --- | --- |
| (가) 아무것도 안 함 | 35.6% (경계 480) | 0 | 기준 |
| (나) PPC UpscaleRT | **100%** (448) | 0 | filter 기본 RetroAA · Point 둘 다 100% |
| (나) PPC PixelSnapping | 35.6% (480) | 0 | (가)와 같음 — 파티클엔 효과 없음(SpriteRenderer 몫) |
| (다) 스냅 셰이더 | **100%** (448) | 0 | (나) UpscaleRT 와 픽셀 단위까지 같은 그림 |
| (라) 스크립트 스냅 | **100%** (456) | 0 | GetParticles → 반올림 → SetParticles |

- 지표 ② 가 모두 0 인 건 흰 단색 텍스처 + MSAA 끔이라서다. 스냅을 안 해도 번지지는 않고 **격자에서 어긋날 뿐**이다.
- 시간열(t=0.313~0.43, 0.013초 간격 열 장)에서 떨림을 봤다.

| 방식 | 4의 배수 아닌 장 | 움직임 |
| --- | --- | --- |
| (가) 없음 | 9/10 | 1~3 px 씩 움직임 — 떨림 |
| (나) UpscaleRT | 0/10 | 4 px 단위로만 뜀 |
| (다) 스냅 셰이더 | 0/10 | (나)와 수열이 똑같음 |
| (라) 스크립트 | 0/10 | 4 px 단위 |

**추천 = (다) 스냅 셰이더.** (나)와 결과가 같은데 게임 카메라·렌더 방식을 바꾸지 않고 이펙트 머티리얼만으로 끝난다. Noise 와 같이 써도 100% 를 지킨다(→ B).
(라)는 매 프레임 스크립트가 돌아야 해서 실게임 비용·누락 위험이 있다. (나) PixelSnapping 은 파티클에 안 먹는다.

스냅 셰이더의 핵심은 정점 셰이더 몇 줄이다. 파티클 렌더러 Custom Vertex Streams 를 Position · Color · UV · **Center** 순으로 두면
TEXCOORD0.zw 와 TEXCOORD1.x 에 입자 중심이 들어온다. 중심만 텍셀 격자에 반올림하고, 네 정점을 같은 양만큼 민다. 쿼드 모양은 그대로다.

```hlsl
float3 wp = TransformObjectToWorld(i.positionOS);
float3 wc = TransformObjectToWorld(float3(i.uvCenter.zw, i.centerZ)); // 입자 중심
if (_Snap > 0.5)
{
    float3 sc = wc;
    sc.xy = round(wc.xy * _PPU) / _PPU; // 중심을 텍셀 격자에 반올림
    wp += sc - wc;                      // 네 정점을 같은 양만큼 이동
}
o.positionCS = TransformWorldToHClip(wp);
```

이 셰이더는 unlit · 알파 블렌드(`SrcAlpha OneMinusSrcAlpha`) 판 하나뿐이다. additive 판 · Lit 판은 아직 없다.

### B. Noise 결정성 · 도트풍 색 수

| 항목 | 결과 |
| --- | --- |
| Noise(strength 1, freq 0.5) t=0.3 · fixedTimeStep=true 두 번 | 해시 같음 |
| 같은 조건 fixedTimeStep=false 두 번 | 해시 같음 |
| fixedTimeStep true vs false | **해시 다름** — 둘 다 결정적이지만 서로 다른 그림 |
| Noise + 스냅 셰이더 | 지표 ① **100%**, ② 0 |
| Noise + 스냅 없음 | 지표 ① 19.3% |
| 4색 2×2 텍스처 Point (크기 8 텍셀) | 배경 뺀 색 수 **4**, 반투명 0 |
| 같은 텍스처 Bilinear | 색 수 **2509**, 반투명 0 |

- **Noise 는 허용한다.** 스냅 셰이더가 Noise 로 흔들린 위치도 격자로 되돌리고, 결정성도 지킨다.
  단 `fixedTimeStep` 값에 따라 그림이 달라지므로 **레시피에 값을 적고 바꾸지 않는다.**
- 도트풍 검수 지표로 「배경 뺀 고유 색 수」가 Point 와 Bilinear 를 확실히 가른다(4 vs 2509).
  반투명 픽셀 수는 불투명 텍스처라 둘 다 0 — 이 판에서는 변별력이 없었다.

### C. additive One One 겹침 밝기

| 입자 수 | 가운데 RGB |
| --- | --- |
| 1개 (색 0.5) | (128,128,128) |
| 2개 겹침 | (176,176,176) |

선형 색공간이라 0.5(sRGB) = 선형 0.214 이다. 둘 더하면 0.428 → sRGB 약 175. **실측 176 이니 가산이 맞다.**
「0.5+0.5 = 1.0(255)」은 감마 공간 계산이라 이 프로젝트에선 나오지 않는다. 겹침 밝기를 예측하거나 검수할 때 선형 기준으로 계산해야 한다.

### D. 2D 빛 · HDR 64bit

| 항목 | 결과 |
| --- | --- |
| Sprite-Unlit-Default | 입자 (255,255,255) |
| Sprite-Lit-Default · 빛 없음 | (255,255,255) — 2D 빛이 하나도 없으면 Unlit 과 같음 |
| Sprite-Lit-Default + Global Light2D 빨강 intensity 0.5 | **(188,0,0)** — 2D 빛을 받는다 (선형 0.5 → sRGB 188) |
| HDR 32bit vs 64bit (투명 배경, 같은 장면) | **PNG 해시 같음**. 배경 알파 0 · 흰 1300 · 반투명 0 둘 다 같음 |

- 검수 장면에 빛이 없으면 Lit/Unlit 차이가 안 보인다. Lit 이펙트를 검수하려면 장면에 Global Light2D 를 넣어야 한다.
- HDR 64bit 결과가 32bit 와 바이트까지 같다 — ③ 의 「HDR 무관」 결론을 받친다.

### 실측 중 밟은 함정

- `PixelPerfectCamera`·`Light2D` 는 `Unity.RenderPipelines.Universal.2D.Runtime` 어셈블리에 있다. asmdef 참조를 빠뜨리면 컴파일 오류가 난다.
- 컴파일 오류로 끝난 판이 `Temp\UnityLockfile` 을 남겼다(Unity 프로세스는 없음). 실행기는 「Unity 프로세스 없음 + 파일을 배타로 열 수 있음」이면 남은 잠금으로 보고 진행해야 한다.
- 첫 스파이크 판에서 새 씬을 연 뒤 지난 씬의 ParticleSystem 을 읽어 예외가 났다(내 코드 버그). 씬을 바꾸면 참조를 다시 잡는다.

## 3. 설계로 넘기는 결정·제약

| 항목 | 정한 것 | 근거 |
| --- | --- | --- |
| 실행 방식 | `-batchmode` 만, `-nographics` 안 씀 | ① |
| 프레임 뽑기 API | `SingleCameraRequest`, 대비책 `Camera.Render()` | ② |
| 후처리 | 뽑는 카메라 `renderPostProcessing = false` 강제. 블룸은 옵션, 기본 끔 | ③ 후처리 켜면 알파가 죽음 |
| HDR 설정 | 건드리지 않음(32·64bit 모두 같음) | ③ · D |
| additive | 알파 블렌드 One One 고정. Zero One 금지 | ③ Zero One 이면 알파 0 |
| 겹침 밝기 계산 | 선형 색공간 기준 | C 128 → 176 |
| 시간 진행 | 프레임마다 `Simulate(t, true, restart:true)` · seed 레시피에 고정 | ④ SHA256 동일 |
| t=0 빈 프레임 | 첫 프레임을 1/fps 부터 뽑거나 i=0 을 빈 그림으로 받아들임 | ④ t=0 은 입자 0개 |
| fixedTimeStep | 레시피에 값 하나를 적고 고정 | B true/false 해시 다름 |
| 픽셀 스냅 | **스냅 셰이더 채택**(Center 스트림, 중심만 반올림). 게임 카메라는 안 바꿈 | A 100% · 떨림 0/10 |
| Noise | 허용 (스냅 셰이더와 함께) | B 100% 유지 · 결정적 |
| 텍스처 필터 | Point · 압축 없음 · PPU 32 | B 4색 vs 2509색 · 게임 저장소 설정 |
| 도트풍 검수 지표 | 「배경 뺀 고유 색 수」 + 「경계 4배수 비율」 | A · B 변별력 확인 |
| 머티리얼 | `Sprite-Unlit-Default`·`Particles/Unlit` 모두 씀. Lit 은 빛 있는 검수 장면에서만 판정 | ④ · D |

조사 문서 5-1 표 1 의 「픽셀 스냅 = Upscale RT 전제」 추천은 이 실측으로 **스냅 셰이더로 바뀐다.** 조사 5-4 의 물음 4(게임 카메라에 Pixel Perfect Camera 전제)는 이제 묻지 않아도 된다.

## 4. 못 본 것

| 항목 | 왜 걸리나 |
| --- | --- |
| 회전·크기 변화 중 스냅 (Rotation · Size over lifetime) | 이번엔 회전 0 · 크기 고정. 회전하면 쿼드가 격자에서 다시 어긋날 수 있다 |
| 홀수 텍셀 텍스처 (예 3×3) | 중심 반올림만으로는 가장자리가 반 텍셀 어긋난다 |
| Lit 판 스냅 셰이더 | 2D 빛을 받는 스냅 셰이더는 안 만들었다 |
| additive 판 스냅 셰이더 | 지금 셰이더는 알파 블렌드 판뿐 |
| 비정수 배율 실제 화면 | 실제 게임 화면(ortho 10 · 1920×1080)처럼 텍셀 배율이 정수가 아닐 때 |
| 반투명 텍스처의 도트풍 지표 | 불투명 텍스처라 반투명 수 지표는 변별력을 못 봤다 |
| HDR 토글이 파이프라인에 실제 반영됐나 | 결과가 같아 반영 여부를 결과로는 못 가름 |
| 여러 층 · 곡선 모듈이 많은 이펙트 | 흰 입자 하나 · 직선 운동 + Noise 까지만 봤다 |
