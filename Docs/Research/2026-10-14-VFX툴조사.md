# VFXTool 조사 — AI 가 Unity 파티클 이펙트를 만들고 보고 고치는 툴 (2026-10-14)

**한 줄 요약** : 「레시피 JSON → 코드로 Shuriken 조립 → 배치 모드로 프레임 PNG → AI 가 보고 고치기」 고리 전체를 묶은 Unity 공개 툴은 없다.
조각(MCP 로 값 넣기 · 스크린샷 · 플립북 굽기 · 논문의 고리 설계)은 다 있으니 **고리와 도트풍 검수를 우리가 만든다.**
가장 큰 위험은 「배치 모드 + URP 2D 에서 실제로 그려지나」이고, 설계 전에 스파이크 넷으로 먼저 가른다.

> 표기 : **[문서]** 공식 문서 · **[포럼]** 포럼·이슈트래커 · **[글]** 블로그·포럼 글 · **[저장소]** ArtTool 안 파일 ·
> **[지식]** 알고 있는 API 동작, 이번에 출처를 다시 찾지 않음 · **[추론]** 근거 없는 짐작 · **[확인 못 함]**.
> **Unity 를 실제로 돌려 본 것은 하나도 없다.**

## 정해진 것

| 항목 | 결정 |
| --- | --- |
| 범위 | Unity 실시간 파티클 (Particle System/Shuriken 1차, VFX Graph 는 뒤로). 도트 프레임 이펙트는 ArtTool 몫 그대로 |
| ArtTool 과 경계 | 방식으로 나눔(A). ArtTool 산출물(플립북 시트·화풍 조각)은 **파일로 입력받기만** 하고 ArtTool 코드를 import 하거나 명령을 호출하지 않는다(스튜디오 공용 규칙 11절) |

| 화풍 맞추기 | **필수.** ArtTool `style extract` 처럼 게임 기준 그림(또는 ArtTool 화풍 조각)에서 팔레트·PPU·픽셀 크기·색 수·외곽선·fps 를 VFX 프로필로 만들고, 레시피 제약과 프레임 검수 둘 다에 쓴다 |

| 실측 자리 | OfficinaTest (`<OfficinaTest 자리>`, 게임과 같은 판) |
| 언어 | Unity 안은 C# UPM 패키지(툴킷 첫 UPM), 바깥 CLI 는 Python(PIL) |

## 1. 남들이 한 것

### 1-1. 도구별 한눈에

**Effekseer** — 게임용 파티클 편집 툴 + 엔진별 런타임.
- 라이선스 : **MIT** (본체·EffekseerForUnity), 무료. 최신 1.80.7 (2026-08-07), 별 약 1.8천.
- Unity 플러그인 : URP 는 `EffekseerRenderPassFeature` 로 지원. 소스에 `UNITY_6000_0_OR_NEWER` · `RecordRenderGraph` 분기가 있다. 개발 시험 프로젝트는 2022.3.62f3.
  **URP 2D Renderer 동작은 확인 못 함.** GPU Particles 는 Unity 에서 아직 안 된다 [문서].
- 파일 : `.efkefc` = 머리 `EFKE` + `INFO`·`EDIT`(에디터 XML 을 zlib 압축)·`BIN_` 덩어리. 옛 `.efkproj` 는 평범한 XML.
  명령줄 `-cui -in x.efkproj -o x.efkefc` 로 창 없이 변환된다(공식 설명). 「XML 을 코드로 쓰고 변환」 길은 **추측, 안 돌려 봄.**
- 우리 길과 겹침 : 고리는 같지만 데이터·재생기가 Effekseer 것. Unity 안에 런타임 플러그인을 하나 더 얹어야 한다(패키지 추가 = 승인).
- 가져올 생각 : 노드 나무 + 물려받기 3단계(늘·생길 때·안 받음) · 모든 수치에 같은 값 모드(고정·랜덤·PVA·Easing·곡선) ·
  트리거 생성(부모 죽을 때) · 편집용 데이터와 실행용 결과를 나눠 두기 · 명령줄 일괄 변환·녹화.

**KanaWorks 「Effekseer 전자동 VFX 파이프라인」** — X 글 둘과 영상뿐.
- 흐름 : 레시피를 코드로 씀 → 컴파일 → Godot 에서 렌더 → **프레임 묶음**을 AI 가 봄 → 고침, 반복. 만든 이펙트 31종.
- 레시피 형식·컴파일 방법·프레임 수·판정 기준·반복 횟수·저장소 : **전부 못 찾음.**
- 가져올 생각 : 한 프레임이 아니라 연번 묶음을 보여 준다. 영상 첫 화면의 전투 이펙트 목록(Light/Heavy/Critical Hit · 속성 베기 · 폭발 · Ice Spikes · Lightning · Vortex · Holy Pillar · Heal · Power Up)은 1차 시험 목록 재료.

**hun0fx Pixel Art VFX Generator (Pixel Studio)** — 3D 이펙트를 픽셀아트 프레임으로 굽는 데스크톱 툴.
- 값 : $24.99 한 번 구매(체험판 있음), 판 1.4. 정식 이용 약관 글은 페이지에 없음. Windows·macOS 베타.
- 1.4 Compose 노드 편집기 : `Resource → Transform / Time / Delay / Color / Pixel → Export`. 직접 만드는 파티클이 **Unity Particle System 모듈 배치를 그대로** 따른다. 레시피 파일 `.h0fx`. `.unitypackage` 파티클 프리팹 가져오기.
- MCP : 「AI 비서가 Compose 레시피를 만들고 묶음 작업을 돌린다」. **도구 이름·입출력은 확인 못 함.** Unity 내보내기 결과물도 확인 못 함.
- 우리 길과 겹침 : 결과가 **구운 그림**이라 겹치지 않는다. 텍스처·플립북 공급자 자리.
- 가져올 생각 : 작은 레시피 파일 · 박자·색을 떼어 낸 후처리 노드 · 시드·묶음 변형 · **「못 옮긴 칸」을 이펙트별로 알려 주기.**

**PixelLab `vfx_workbench`** (예비 길) — 메인 세션이 describe start/parts/recipe 만 읽음, 생성 0회.
- 무엇 : AI 가 레시피 JSON(겹·파츠)을 쓰면 서버가 프레임을 그리는 **절차 렌더러.** 구독자는 무료, 크레딧 안 씀.
- 규모 : 파츠 약 110개 · 겹 종류 15 · canvas 16~1024 · frames 1~32 · fps 1~60. 값은 모두 animated value(숫자 | from/to+ease | keys | wave | expr), 색은 ramp(2~12색)로만.
- 결과 : GIF + 시트 PNG + JSON, `--game-pack` 이면 파츠별 클립 ZIP + manifest.json.
- 우리 길과 겹침 : 산출물이 스프라이트 프레임. 막혔을 때 우회 길이고, Unity 에선 TextureSheetAnimation 이나 SpriteRenderer 애니로 돌린다.
- 가져올 생각 : animated value 꼴(MinMaxCurve JSON 표현의 본보기) · 「파츠 + 슬라이더」 = 「프리셋 + 노출 파라미터」 · 응답마다 접촉판으로 모든 프레임 보여 주기.
- 못 본 것 : describe craft·cookbook·presets·tools, 실제 render 품질·속도.

**CoplayDev/unity-mcp (MCP for Unity)** — MIT · ★14940 · pushed 2026-10-08 · README 최신 v10.3.0.
- `manage_vfx` 의 `particle_*` action : create · get_info · set_main · set_emission · set_shape · set_color/size/velocity_over_lifetime · set_noise · set_renderer · enable_module · add/clear_burst · 재생 조작. 값은 `properties` 사전에 Unity 필드 이름 그대로. **손으로 짠 모듈만** 받는다.
- VFX Graph(`vfx_*`)는 **템플릿 .vfx 를 복사 + 노출 속성 값 바꾸기**까지만.
- 결과 확인 : `manage_camera` `screenshot`(base64 PNG 인라인 · surround 6각도). `Simulate` 호출은 Vfx 코드에서 못 찾음.
- Coplay 블로그(2026-01-22) : 레시피 라이브러리 · 텍스처 생성 · 3초 돌려 **입자 가장 많은 한 프레임**을 보고 판정. 한계로 「한 프레임으론 움직임·타이밍을 못 본다」. 레시피 스키마 비공개.

**IvanMurzak/Unity-AI-ParticleSystem** — 확장 MIT(★54, pushed 2026-10-12, v1.2.19), 본체 Unity-MCP 는 Apache-2.0(★4447).
- `particle-system-get` · `particle-system-modify` 둘. **24개 모듈 전부**를 `SerializedMember` 로 받아 리플렉션으로 넣는다. 넣은 모듈만 바뀐다. 6000.3 시험 통과 표시.
- 결과 확인 방법은 확장 문서에 없음(본체에 screenshot 도구 넷).
- 가져올 생각 : 「모듈마다 부분 diff 적용」 = 우리 patch 적용기 모양.

**ParticleGen** (논문, Unreal Niagara, arXiv 2608.00629, 2026-08-01) — **우리 고리의 설계 본보기 1순위.** 코드 공개 확인 못 함.
- Planner(뼈대 : 이미터별 material·renderer·모듈 순서, 값은 비움) → Generator(이미터마다 값 채움, 필요한 모듈 문서만 줌) →
  FxConverter(JSON → 에셋, **컴파일 오류 회수**) → 정해진 장면 렌더 → 프레임 몇 장 → Critic(의미 점수 0~1 + 움직임·겉모습 지적, 2회차부터 전 판과 견줌) →
  DRAG(증상 ↔ 원인 파라미터 표 검색) → Refiner(JSON patch).
- 멈춤 : 점수 > 0.9 또는 4회. 효과 없는 patch 는 rollback, **역대 최고점 판을 돌려줌.**
- 수치 : 사용자 의미 점수 3.255 → 3.680(1회) → 4.420(전체), 기술 아티스트 20명 블라인드. DRAG 를 빼면 원인을 잘못 짚음.

**vfx-flipbook-baker** (Kan2nist) — MIT · ★0 · 만든·pushed 2026-06-04.
- Shuriken·VFX Graph → 투명 PNG 시트. **프레임마다 절대 시간으로 `Simulate`, 고정 seed.** 경계를 전 프레임에서 먼저 재고 카메라를 한 번 맞춤(2패스).
  알파 둘 : 투명 1회(알파 블렌드), **검정·흰 배경 2회 렌더 차이로 알파 복원(가산 블렌드).** one-shot 길이 = duration + 최장 lifetime.
- 에디터 창 도구라 `-batchmode`·URP 2D 동작은 확인 못 함. 1인 작품이라 코드는 직접 읽고 판단.

### 1-3. 아무도 안 한 것 = 우리 몫 셋

1. **공개된 Shuriken 레시피 형식 + 조립기** — 사람·AI 가 쓰기 쉬운 줄임 표기, 검증기, 「못 옮긴 칸」 보고. 오픈소스 라이브러리를 못 찾았다.
2. **배치 모드 결정적 연번 렌더 + 판정** — 고정 seed · 절대 시간 샘플링 · 접촉판 한 장. 한 프레임이 아니라 움직임까지 본다. Coplay 의 한계를 정면으로 푸는 자리.
3. **URP 2D · 도트풍 전제의 고리 관리** — 화풍 프로필 검수, Shuriken 용 「증상 ↔ 원인 파라미터」 표, patch · rollback · 최고점 보관. 어디에도 없다.

## 2. Unity 쪽 기술 조사

### 2-1. 코드로 조립하기

- **Inspector 모듈은 거의 다 스크립트 API 가 있다** [지식]. IvanMurzak 확장이 24개 모듈 전부를 읽고 쓰는 것이 방증 [문서].
  Inspector 에만 있고 API 에 없는 값은 이번에 **찾은 것 없음 [확인 못 함]** (있으면 `SerializedObject` 로).
- 모듈은 struct 래퍼라 지역 변수에 받아 고치면 바로 반영된다 [지식].
  ```csharp
  var main = ps.main;          // ps.main = ... 통째 대입은 안 된다
  main.startLifetime = 0.6f;
  ps.emission.SetBursts(new[] { new ParticleSystem.Burst(0f, 30) });
  ```
- `MinMaxCurve` 4모드(상수 · 두 상수 랜덤 · 곡선×multiplier · 두 곡선 랜덤), `MinMaxGradient` 4모드 [지식]. **Gradient 색 키·알파 키는 각각 최대 8개** → 검증기에서 막는다.
- 시드 : `useAutoRandomSeed = false; randomSeed = 1234;` — **멈춘 상태에서만** 바꿀 수 있다 [지식].
- 프리팹 : `PrefabUtility.SaveAsPrefabAsset`. **그 전에 머티리얼·텍스처를 `AssetDatabase.CreateAsset` 으로 에셋 저장**해야 참조가 안 빈다 [지식].

까다로운 자리 [지식] :
- Trails 는 렌더러에 `trailMaterial` 을 따로 넣어야 보인다.
- SubEmitter 대상은 자식 GameObject 로 두는 게 안전하다 (세부 확인 못 함).
- 오브젝트·에셋을 가리키는 값(Collision planes · Lights 프리팹 · Mesh shape · Trigger colliders)은 이름으로 찾는 층이 필요 → 1차 제외.
- Custom Vertex Streams 는 셰이더와 짝이 맞아야 함 → 1차 제외.

### 2-2. 배치 모드에서 프레임 뽑기

- **`-nographics` 는 못 쓴다.** 그래픽 장치를 초기화하지 않아 회색·빈 화면이 된다 [문서]. → GPU 있는 PC 에서만 돈다.
- `-batchmode` 만 쓰면 장치가 살아 있다 — 장치가 꺼지던 버그는 5.5.2 에서 고쳐졌다는 보고 [포럼]. 2016년 「batchmode 는 렌더 안 함」 Won't Fix 이슈도 있으나 옛 판.
  **Unity 6.3 + URP 2D + 이 PC 에서 되는지는 확인 못 함 — 첫 실측 과제.**
- 배치 모드에선 카메라가 저절로 안 그린다. 코드로 렌더를 불러야 한다 [문서, PolySpatial].
- URP 수동 렌더 (Unity 6) [문서] :
  ```csharp
  var req = new UniversalRenderPipeline.SingleCameraRequest();
  if (RenderPipeline.SupportsRenderRequest(cam, req)) {
      req.destination = rt;
      RenderPipeline.SubmitRenderRequest(cam, req);   // 동기
  }
  // RenderTexture.active = rt; tex.ReadPixels(...); tex.EncodeToPNG()
  ```
  - `StandardRequest`(카메라 스택) · `SingleCameraRequest` · `ObjectIdRequest`(에디터 전용). `RenderSingleCamera` 는 obsolete.
  - 렌더 루프 콜백 안에서 부르면 「Recursive rendering is not supported in SRP」 [포럼] → 루프 밖에서 부른다.
  - **2D 렌더러에서 `SingleCameraRequest` 가 되는지 확인 못 함.** 문서 예시는 Universal Renderer 기준. 대안 `Camera.Render()` 가 URP 에서 동작한다는 말은 공식 확인 못 함.
- **시간 고정** : `ps.Simulate(t, withChildren:true, restart:true, fixedTimeStep:true)` 로 0 부터 t 초까지 돌리고 멈춘다 [문서]. 프레임 i 에 `t = i/fps` → 결정적.
  플레이 모드 없이 `-executeMethod` 에서 바로 돌릴 수 있다 [지식, 배치에서 실측 안 됨]. `fixedTimeStep:true` 는 Fixed Timestep(기본 0.02초) 간격이라 60fps 와 어긋날 수 있어 true/false 비교가 필요하다 [확인 못 함].
  vfx-flipbook-baker 도 같은 방식(절대 시간 점프 + 고정 seed)을 쓴다.
- **Unity Recorder 는 고르지 않는다** : 공식 길이 플레이 모드 녹화이고 `-batchmode` 동작은 문서에 없다 [문서]. 알파는 Targeted Camera 에서만.

### 2-3. 알파 함정 셋 [지식, 실측 필요]

1. URP 에셋 HDR 정밀도가 32bit(R11G11B10)면 컬러 버퍼에 **알파가 없다.** 64bit 로 두거나 HDR 를 끈다.
2. 후처리(특히 FXAA)가 알파를 망가뜨린다 [이슈트래커]. Recorder 문서도 URP 17+ 는 「Alpha processing」 설정을 보라고 한다 [문서]. 뽑는 카메라는 후처리를 끈다.
3. **Additive 파티클은 알파를 거의 안 쓴다** → 투명 PNG 에선 안 보인다. 후보 : (a) 검은 배경 밝기를 알파로, (b) 검정·흰 두 번 그려 복원(vfx-flipbook-baker 방식), (c) 판정은 불투명 배경 PNG 로만.

투명 배경 자체는 Solid Color `(0,0,0,0)` + ARGB32 RT 로 원리상 된다 [지식].

### 2-4. 2D 렌더러의 파티클 머티리얼

- 2D 빛을 받는 기본은 `Sprite-Lit-Default`, 안 받는 건 `Sprite-Unlit-Default` [문서].
- **URP `Particles/*` 셰이더에 대해 재료끼리 말이 다르다.**
  재료 1 : 2D 렌더러에서 어떻게 되는지 공식 문서로 **확인 못 함**, `Particles/Lit` 는 2D 빛을 못 받는다고 보는 게 안전 [지식].
  재료 6 : 「2D 렌더러에서 지원 안 되어 단순 unlit 으로 떨어진다」 [글, Unity 이슈 답변]. → **실측으로 가른다.**
- 커스텀 Sprite-Lit 셰이더 파티클이 2D 빛을 안 받던 Render Graph 버그는 6000.3.0b10 · 6000.4.0a5 에서 고쳐졌다 [문서]. 우리 판 6000.3.23f1 은 그 뒤다.
- 이펙트는 대개 스스로 빛나니 1차는 **unlit + 2D 빛 무시**가 단순하다. 정렬은 `sortingLayerName`·`sortingOrder` [지식].

### 2-5. Shuriken vs VFX Graph

- VFX Graph 는 Unity 6 에서 URP 2D 와 같이 쓸 수 있고 `VFXSpriteLit` 등으로 2D 빛도 받는다 [문서].
- 그러나 **노드를 코드로 만드는 공개 API 가 없다** — Unity 담당자 답(2023-10-24) [포럼]. 내부 API(asmref)로는 되지만 「공식 지원 아님, 판마다 바뀜」, Unity 6(VFX 17)에서 되는지 확인 못 함.
  공개로 되는 것은 템플릿 등록·노출 속성 값뿐. compute shader 가 필요해 못 쓰는 대상도 생긴다 [지식].
- **판단 : 1차는 Shuriken.** 모듈 값이 다 열려 있고, `Simulate` 로 시간을 고정하고, 2D 정렬과 오래 써 온 길이고, 플랫폼 제약이 없다.
  VFX Graph 는 「입자 수만 개」가 꼭 필요할 때 「템플릿 그래프 + 노출 속성 레시피」로 2차에.

### 2-6. 레시피 JSON

1차 최소 집합 (이펙트 하나 = 시스템 1~N 개) :

| 묶음 | 값 |
| --- | --- |
| 이펙트 공통 | `name` · `duration` · `fps` · `seed` · `canvas`(px · orthoSize) · `background` |
| Main | `duration` · `loop` · `startDelay` · `startLifetime` · `startSpeed` · `startSize` · `startRotation` · `startColor` · `gravityModifier` · `simulationSpace` · `maxParticles` |
| Emission · Shape | `rateOverTime` · `bursts[]` / `type`(Circle·Cone·Sphere·Box·Edge) · `radius` · `angle` · `arc` · `position` · `rotation` |
| Over Lifetime · Noise | color · size · velocity(x·y·radial) · rotation / `strength` · `frequency` · `scrollSpeed` |
| Renderer · 자식 | `renderMode` · `material`(이름표) · `blend` · `texture` · `sortingOrder` / `children[]` 재귀 |

뒤로 미룰 값 : Trails · SubEmitters · TextureSheetAnimation · Collision · Triggers · Lights · External Forces · Inherit/Limit Velocity · Force over Lifetime · Custom Vertex Streams · Custom Data · Mesh shape · 2D 빛 머티리얼.

값 적는 꼴 — Unity 모드를 그대로 옮긴 다형 값 :
```json
"startSize": 0.3
"startSize": { "random": [0.2, 0.5] }
"sizeOverLifetime": { "curve": [[0, 0], [0.2, 1], [1, 0]], "mult": 1.0 }
"colorOverLifetime": { "color": [[0, "#FFE08A"], [1, "#401000"]], "alpha": [[0, 1], [1, 0]] }
```
- 곡선 키 `[t, v]` 짧은 배열이 AI 가 쓰기 쉽다. 탄젠트는 빼고 자동 평활. 다른 꼴 `{ "t":, "v": }` 은 길지만 실수가 적다.
- **`JsonUtility` 는 「숫자 또는 객체」 다형 값과 Dictionary 를 못 읽는다** [지식]. 위 꼴을 쓰려면 `com.unity.nuget.newtonsoft-json`(Unity 공식) 이 필요하다 — **패키지 추가라 사용자 승인.**
  안 쓰면 모든 값을 늘 `{ "mode": "const", "v": 0.3 }` 꼴로 통일한다.
- `EditorJsonUtility.ToJson` 으로 기존 시스템을 덤프할 수는 있으나 내부 이름이라 레시피로는 안 맞다 — 역변환 도구 재료 정도 [지식, 덤프 품질 확인 못 함].
- 이름은 Unity 필드 이름을 따른다(Coplay `properties` · hun0fx Compose 가 같은 배치). 사람·AI 모두 익숙하다.

## 3. 도트풍

### 3-1. ArtTool 이 이미 정한 도트 이펙트 기준 [저장소]

| 기준 | 내용 |
| --- | --- |
| 흐름 | 대비(어둠) → 흰 번쩍 → 모양 → 사라짐. 최소 4프레임 |
| 장수·길이 | 이펙트 3~7장, 한 장 **60~80ms** (캐릭터·배경은 100~120ms) |
| 색 | 흰 1색으로 모양을 먼저, 색은 나중. 대부분 1색, 큰 반짝임·레이저 3색. 게임 팔레트 밖 색이어도 됨 |
| 외곽선 · 반투명 | 이펙트는 `outline: none` 고정 · 알파는 0/255 만 |
| 입자 | 1~2px 점이 퍼지며 사라진다. 「입자 겹(드문 1px 점)」이 따로 있다 = 파티클 몫 |
| 회전 | 「도트는 회전하지 않는다」 — 파티클 Rotation 과 정면으로 부딪친다 |
| 반복 · 불·연기 | 반복은 시작을 어긋나게(= 시작 프레임 랜덤) · 불은 빨리, 연기는 천천히 |

ArtTool fx 템플릿 넷(`fx_ring_burst` · `fx_sparkle` · `fx_dust` · `fx_swirl`)은 `kind · sizes · values · frames[].draw[] · check · fixed · must · presets` 꼴이고,
**플립북 텍스처의 밑판**으로 쓸 수 있다 [추론].

> **재료와 정해진 것이 어긋나는 자리** : 도트풍 재료는 「VFXTool 이 빌릴 ArtTool 명령」(`template render` · `check` · `sheet --strip` · `tint` · `merge-colors`)을 적었다.
> 정해진 경계는 **ArtTool 명령을 호출하지 않는다**이다. 그래서 이 명령들은 **ArtTool 쪽에서 사람·AI 가 돌려 파일을 만드는 단계**로만 보고, VFXTool 은 그 결과 PNG·JSON 을 입력으로 받는다.

### 3-2. 실시간 파티클로 도트풍 내기

- **Pixel Perfect Camera(URP 내장) + Upscale Render Texture** 가 가장 확실하다 — 기준 해상도에 그린 뒤 키워 「unaliased and unrotated pixels」 [문서].
  대신 Pixel Snapping 을 못 쓰고, 반 픽셀 입자가 1px 씩 떨릴 수 있다 [추론]. Pixel Snapping 은 문서가 Sprite 만 말해 **파티클에 먹는지 확인 못 함.**
- 스크립트 스냅(`GetParticles` → 위치 반올림 → `SetParticles`)은 [추론], CPU 비용. 셰이더 스냅은 들쭉날쭉·「헤엄침」 보고 [글].
- 파티클은 스프라이트 PPU 를 무시하고 Start Size 를 쓴다 → **Start Size = 텍스처 px / PPU** 로 계산해야 1:1 [글 + 추론].
- 텍스처는 Filter Point · 압축 없음 · mipmap 끔 [글]. 흰 1×1·2×2 + Start Color 로 물들임.
- Color over Lifetime 을 **`GradientMode.Fixed`** 로 두면 색·알파가 계단이 된다 [문서]. 플립북은 Time Mode FPS 12~16, Frame Blending 끔 [문서 + 추론].
- 「위치를 계단으로」(고정 간격 `Simulate(dt, true, false)` 수동 진행)는 실제 도트 게임 사례 **확인 못 함** [추론].
- 2D 빛은 도트 위에 그러데이션을 얹어 색 수를 늘린다. 색 단계를 막는 공개 예는 확인 못 함 [추론]. 팔레트 LUT·포스터라이즈 파티클 전용 예도 확인 못 함.
- 유명 도트 게임(Dead Cells · Celeste · Hyper Light Drifter)의 파티클 방식은 공개 자료 확인 못 함.

### 3-3. 1차가 지킬 규칙 후보 10

| # | 규칙 | 근거 수준 |
| --- | --- | --- |
| 1 | 텍스처 Point · 압축 없음 · mipmap 끔 · 게임 PPU | 문서·글 |
| 2 | 입자 크기 = 텍스처 px / PPU 의 정수배. Size over Lifetime 도 정수 px 계단 | 글 + 추론 |
| 3 | Rotation · Rotation over Lifetime 끔 | 저장소 |

| 5 | 플립북 Time Mode FPS 12~16, Frame Blending 끔 | 저장소 + 문서 |
| 6 | 흰 1색 텍스처 + Start Color. 한 이펙트 색 수 ≤ 3 | 저장소 |
| 7 | 큰 모양 이펙트는 「대비 → 흰 번쩍 → 모양 → 사라짐」, 3~7장 | 저장소 |

### 3-5. 레시피 도트 전용 값 · 화풍 프로필

재료가 낸 도트 전용 값 : `ppu` · `pixel_size`(1~4, Start Size = pixel_size/ppu) · `size_steps` · `rotation`(기본 false) · `color_steps`(Fixed 로 구움, 알파 0/1) ·
`max_colors`(1~3, ArtTool 과 같은 낱말) · `flipbook{texture, tiles_x, tiles_y, fps, random_start_frame, source_template}` · `frame_ms`/`fps`(60~80ms 검사) ·
`sim_step` [추론] · `snap`(`upscale_rt`·`script`·`none`) · `material`(`sprite_unlit`·`sprite_lit`·`custom_pixel`) · `blend`(`alpha_cutout` 기본).

**정해진 결정(화풍 맞추기 필수)과 엮으면** — 값을 둘로 나눈다 :
- **VFX 프로필이 채우는 값** : 팔레트 · `ppu` · `pixel_size` · `max_colors` · 외곽선(이펙트는 none 고정) · `fps`/`frame_ms`. 게임 기준 그림이나 ArtTool 화풍 조각 파일에서 뽑는다.
- **레시피가 고르는 값** : 모양·움직임·`size_steps`·`color_steps`(팔레트 안에서)·`flipbook`·`snap`·`material`·`blend`.
- 프로필은 **두 번** 쓴다 : ① 조립 전 레시피 검증(정수배·회전·색 수·fps 범위) ② 뽑은 프레임 검수(색 수 · 팔레트 밖 색 · 반투명 칸 · 입자 크기).

### 4-3. DataTool verify 에서 빌릴 것 / 못 쓰는 것

툴끼리 코드로 묶지 않으니 **꼴만 따라 새로 짠다.**

| 빌릴 꼴 | 내용 |
| --- | --- |
| Unity 찾기 | `ProjectVersion.txt` → `C:\Program Files\Unity\Hub\Editor\<판>\Editor\Unity.exe`, 인자로 덮기 |
| 잠금 검사 | 에디터가 열려 있으면 멈춤 |

### 4-4. ArtTool sheet · draw 고리에서 따를 생각

코드 복사·호출 없이 설계만 따른다. `vfxtool sheet` 는 Pillow 로 새로 짠다(약 100~150줄).
1. 여러 장을 작은 칸으로 이어 붙인 한 장 — VFX 는 **시간 띠 + 어두운·밝은 배경 두 줄 + 칸마다 시간 이름표.**
2. 줄마다 숫자 보고 — 덮은 면적 % · 최대 밝기 · 무게중심 · 알파 합 · 첫·끝 프레임이 비었나 (`vfxtool measure`).
3. 바퀴 상한(ArtTool 은 3바퀴) + 바퀴마다 PNG 남기기.
4. `{status, issues:[...], counts, metrics}` 보고 꼴.

`grid show --shrink`·좌표 린트는 64칸 이하 도트 격자용이라 안 맞는다 — 파티클은 반투명·가산이 많아 alpha_px·orphan 이 전부 걸린다.

### 4-5. CodeTool asmdef · UPM 길

- CodeTool `Template/` 은 `install.ps1` 로 복사 + 네임스페이스 치환, asmdef 두 벌(Runtime · Editor) 본보기.
- UPM 이면 치환이 필요 없다(네임스페이스 `Officina.Vfx` 고정). 게임 `manifest.json` 에
  `"com.officina.vfx": "file:../../Tools/VFXTool/Unity/com.officina.vfx"` 한 줄 → 서브모듈 갱신만으로 C# 도 같이 바뀐다.
- 다른 길 : ArtTool `ui bake` 처럼 C# 을 복사하고 사람이 고친 건 `.new` 로 옆에. UPM 을 정했으니 참고만.

### 5-2. 실측 스파이크 넷 (설계 전, 1시간 안쪽, OfficinaTest)

1. `-batchmode` + `-executeMethod` 로 빈 2D URP 씬에 파티클 하나 → PNG 1장이 회색이 아닌가.
2. 2D 렌더러에서 `RenderPipeline.SupportsRenderRequest(cam, new SingleCameraRequest())` 결과. 안 되면 `Camera.Render()`.
3. Solid Color (0,0,0,0) + ARGB32 RT 로 알파가 살아 나오나 (URP 에셋 HDR 설정별).
4. `Simulate(t, true, true, true/false)` 로 같은 t 를 두 번 뽑아 픽셀이 같은가.

여유가 되면 같이 볼 것 : Particles 셰이더가 2D 렌더러에서 어떻게 나오나(재료 어긋남), Upscale RT 위 Noise·additive 가 화풍 검수를 통과하나.

- 화풍 프로필 추출(`profile`)은 파이썬 쪽 몫으로 둘 자리가 아직 초안에 없다 — 설계에서 넣는다.

### 5-4. 사용자에게 물을 것

1. **Newtonsoft(`com.unity.nuget.newtonsoft-json`) 추가** — 짧은 다형 꼴을 쓸지, JsonUtility 로 늘 객체 꼴로 갈지.
2. **블룸을 쓸지** — 게임 렌더러에 PostProcessData 가 비어 있다. 쓰면 게임 쪽 설정 변경이고, 뽑는 카메라 알파 처리도 달라진다.
3. **1차 시험 이펙트 목록** — 후보 : KanaWorks 목록(타격 3단 · 속성 베기 · 폭발 · 기둥 · 회복 · 버프) 중 파티클 몫(파편·불똥 · 흙먼지 · 반짝임 · 분위기 입자 · 회복 입자).
4. **게임 카메라에 Pixel Perfect Camera + Upscale RT 를 전제해도 되나** — 게임 저장소 설정에 걸린다.
5. **vfx-flipbook-baker(MIT) 코드 일부를 가져올지** — 가져오면 THIRD-PARTY 에 적는다. 방식만 따를 수도 있다.
6. **PixelLab 우회 길을 언제 쓰나** — 「자체 제작이 막혔다」의 기준(예 : 바퀴 상한을 넘김).
